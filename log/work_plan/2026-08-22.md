## Added — `sb_apply`

You edit `~/.config/silverbullet/env`, then `nix run .#sb_apply` swaps the process.
It checks the file **before** killing anything, so a bad edit costs nothing.

Rejects: missing/commented `SB_USER`, no `:`, empty user, empty password. All four tested,
old process kept serving each time.

Two bugs found while testing:

- **`pkill -f silverbullet.js` kills your own shell.** `-f` matches the whole command line,
  so any shell that merely *mentions* the string dies too. It killed mine mid-test. Now it
  reads the PID holding port 35909 out of `ss` and kills only that.
- **`302` from `/.auth` does NOT mean login succeeded.** SB redirects on failure too, to
  `/.auth?error=1`. Real signals:
  - success -> redirect to `/`, cookie set, `/.fs/<page>` = 200
  - failure -> redirect to `/.auth?error=1`, no cookie, `/.fs/<page>` = 401

  Earlier "302 = logged in" checks in this log were measuring nothing.

Proved both directions: env `SB1` -> SB1 gets 200, SBTEST 401; env `SBTEST` -> reversed.
Env restored to `SB1`, untouched.

`sb_apply` starts SilverBullet with `nohup`, so its parent is PID 1 — it survives logout,
unlike the plain `&` that dropped it earlier.

**GUI had no password.** `<gui>` carried no `<user>`/`<password>` — publishing it that way
hands anyone full admin over sync. Set first, with
`syncthing generate --gui-user=ryu --gui-password=-` (password on stdin, not argv, so it
stays out of history and `ps`). Syncthing must be stopped for that; it rewrites config.xml.

Two things the official docs' nginx snippet gets wrong for this setup:

- **`proxy_set_header Host $host` gives 403.** Syncthing's DNS-rebinding check only trusts
  a localhost Host while bound to loopback. Verified: `Host: ryuora144.duckdns.org` -> 403,
  `Host: localhost` -> 200. Using `Host localhost`, not `$host`. The alternative is
  `insecureSkipHostcheck` in config.xml, which is worse.
- Trailing slash on both `location /syncthing/` and `proxy_pass .../` is what strips the
  prefix. Without it every path arrives doubled.

Subpath is safe here because the GUI is embedded in the binary and builds **relative**
`rest/...` URLs. Assets resolve under `/syncthing/` and return 200.

Verified the real browser flow: GET page (sets `CSRF-Token-X4M3SC2`) -> POST
`/rest/noauth/auth/password` (204, sets `sessionid-X4M3SC2`) -> `rest/system/status` with
the `X-CSRF-Token-X4M3SC2` header -> 200. Wrong password -> 403. No credentials -> 403.

subdomain still 401.

## Added — `st_passwd`

`nix run .#st_passwd` — prompts for GUI user + password (twice, hidden), stops syncthing,
rewrites the login, restarts detached, then **proves the new password logs in** before
saying ok.

Different shape from `sb_apply` on purpose: SilverBullet reads a plaintext env file, so you
edit and it applies. Syncthing stores a bcrypt hash inside `config.xml`, so there is
nothing to hand-edit — the script has to own the whole change.

- password on **stdin**, never argv — argv is visible in `ps` and lands in shell history
- typed twice, empty rejected
- `"` and `\` rejected — the login check posts JSON, and escaping them is not worth a jq dep
- syncthing killed **by port owner**, not `pkill -f syncthing`, same footgun as before
- `generate` needs syncthing stopped; it rewrites `config.xml` underneath it

Tested. Four rejection paths (empty user, mismatch, empty password, quote) all exit 1 with
the old process untouched. Real change verified over https: new password 204 / old 403,
then restored: original 204 / temp 403. Restart is detached — supervisor's parent is PID 1.

Stack after: main site 200, `/syncthing/` 200, sb `/.fs/` 401.
