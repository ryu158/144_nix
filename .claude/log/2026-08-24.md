## Built
`st_ps_update` (`my_wiki_servers/syncthing/flake.nix`) no longer does
`read -rp`/`read -rsp`. It now reads `<user>`/`<password>` straight out of
`~/.local/state/syncthing/config.xml`'s `<gui>` block, kills the process (port owner
via `ss`, same as before), applies, restarts, and — only when the password it read
was still plaintext — proves login works. An already-hashed password just gets
applied + restarted, no re-verify.

## Things that bit, in order
- **Plan's core assumption was wrong.** Planned on "syncthing hashes a plaintext
  `<password>` itself on next startup." False — it just fails auth (`Bad credentials
  supplied`, 403 on login). First real run left the live GUI logged-out.
- **`syncthing generate` silently no-ops.** Given `--gui-password=-`, if the
  plaintext matches what's already sitting in `<password>` (byte-for-byte), it skips
  the write — no "Updated GUI authentication password" log line, no error either.
  This design reads `$p1` out of config.xml and feeds that exact value back into
  `generate`, so the skip fired **every single time** — confirmed by testing with a
  different username (worked) vs. the same username+password (silently skipped).
  Fix: blank `<password>` in config.xml first, then call `generate` — forces the
  hash write unconditionally.
- JSON body for the login-proof POST now built with `jq -n --arg` instead of raw
  `"{\"username\":\"$u\"...}"` string interpolation — removes the old restriction on
  `"`/`\` in the password (jq escapes correctly; no user prompt to reject at anyway).
