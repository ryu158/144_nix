## Version pin — why 25.11 and not 24.05
1. 24.05 ships silverbullet 0.7.7 (pre-2.0 architecture, incompatible space format) and
   syncthing 1.27.7 (pre-SQLite-rewrite).
2. 25.11 ships 2.0.0 and 2.0.10.
3. Both server flakes pin 25.11 alone.
4. Nothing else in the repo moves off 24.05.

## Things that bit, in order
1. **`substituteAll` is removed in 25.11.** nginx/ (24.05) still uses it fine. The two new
   flakes cannot — they use `runCommand` + `sed`.
2. **`--no-default-folder` gone in syncthing 2.x.** Service exited 80 until dropped.
3. **`. env` does not export.** Needs `set -a; . file; set +a`, or `SB_USER` never reaches
   the process and the wiki serves with NO login. Silent — the site still answers 200.
4. **`pkill -f silverbullet.js` kills your own shell.** `-f` matches the whole command line,
   so any shell that merely mentions the string dies. It killed mine. Both apps now read the
   PID off the listening port via `ss` and kill only that.
5. **`302` from SB `/.auth` does not mean success.** SB redirects on failure too, to
   `/.auth?error=1`. Real check: `/.fs/<page>` = 200 with cookie, 401 without.
6. **Syncthing 403s `Host: ryuora144.duckdns.org`.** DNS-rebinding check only trusts
   localhost while bound to loopback. nginx sends `Host localhost`, NOT `$host` — the
   official syncthing docs snippet is wrong for a loopback bind.
7. **`.gitignore` with `my_wiki/` never works.** git does not descend into an excluded dir,
   so `!my_wiki/CLAUDE.md` is unreachable. Needs `my_wiki/*`.
8. **SB shell backend defaults ON.** A page could run commands on the box, internet-facing.
   Set `SB_SHELL_BACKEND=off`.
9. **Syncthing GUI had no password.** Set one before opening the route, not after.

## Dropped: systemd
1. User's call.
2. Both user units removed, `configs/` and `scripts/` deleted from both server dirs.
3. Each flake is now devShell + start script + password app, nothing else.
4. Cost: nothing starts on boot.
5. Both apps restart with `nohup`, so a running server survives logout — but a reboot needs
   a manual start.

## Password apps
1. `sb_ps_update` and `st_ps_update`. Same job, different input on purpose.
2. SB reads plaintext `SB_USER` from a file you edit; syncthing keeps a bcrypt hash, so its
   app prompts.
3. Deliberately did NOT give syncthing an env file — that would put a plaintext password on
   disk where none exists today, buying only symmetry.
4. Both validate before killing anything, so a bad input costs nothing.
