## Version pin — why 25.11 and not 24.05
24.05 ships silverbullet 0.7.7 (pre-2.0 architecture, incompatible space format) and
syncthing 1.27.7 (pre-SQLite-rewrite). 25.11 ships 2.0.0 and 2.0.10. Both server flakes
pin 25.11 alone. Nothing else in the repo moves off 24.05.

## Things that bit, in order
- **`substituteAll` is removed in 25.11.** nginx/ (24.05) still uses it fine. The two new
  flakes cannot — they use `runCommand` + `sed`.
- **`--no-default-folder` gone in syncthing 2.x.** Service exited 80 until dropped.
- **`. env` does not export.** Needs `set -a; . file; set +a`, or `SB_USER` never reaches
  the process and the wiki serves with NO login. Silent — the site still answers 200.
- **`pkill -f silverbullet.js` kills your own shell.** `-f` matches the whole command line,
  so any shell that merely mentions the string dies. It killed mine. Both apps now read the
  PID off the listening port via `ss` and kill only that.
- **`302` from SB `/.auth` does not mean success.** SB redirects on failure too, to
  `/.auth?error=1`. Real check: `/.fs/<page>` = 200 with cookie, 401 without.
- **Syncthing 403s `Host: ryuora144.duckdns.org`.** DNS-rebinding check only trusts
  localhost while bound to loopback. nginx sends `Host localhost`, NOT `$host` — the
  official syncthing docs snippet is wrong for a loopback bind.
- **`.gitignore` with `my_wiki/` never works.** git does not descend into an excluded dir,
  so `!my_wiki/CLAUDE.md` is unreachable. Needs `my_wiki/*`.
- **SB shell backend defaults ON.** A page could run commands on the box, internet-facing.
  Set `SB_SHELL_BACKEND=off`.
- **Syncthing GUI had no password.** Set one before opening the route, not after.

## Dropped: systemd
User's call. Both user units removed, `configs/` and `scripts/` deleted from both server
dirs. Each flake is now devShell + start script + password app, nothing else.
Cost: nothing starts on boot. Both apps restart with `nohup`, so a running server survives
logout — but a reboot needs a manual start.

## Password apps
`sb_ps_update` and `st_ps_update`. Same job, different input on purpose:
SB reads plaintext `SB_USER` from a file you edit; syncthing keeps a bcrypt hash, so its
app prompts. Deliberately did NOT give syncthing an env file — that would put a plaintext
password on disk where none exists today, buying only symmetry.
Both validate before killing anything, so a bad input costs nothing.

## Verified end to end
SB: form login -> cookie -> PUT through nginx/TLS -> `my_wiki/1st/n/scratch.md` on disk
with exact bytes -> GET returns it. Scratch deleted.
Syncthing: GET page (CSRF cookie) -> POST auth (204) -> `rest/system/status` with the
`X-CSRF-Token-X4M3SC2` header -> 200. Wrong password 403.
Password round-trips both services: new 204/200, old 403/401, then restored.
webUI untouched: `/`, `/interpolate_cal`, `/interpolate_blog`, `/dev_basic/` all 200.
