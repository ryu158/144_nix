## The plan, and the two questions that shaped it

## applyColumnLock was wrong, not unproven

The handover flagged this branch as untested. It was worse than that.

`setData` hard-resets `numCols` from the incoming array, so a locked grid moved
in **both** directions. The existing code truncated a too-wide file, which is
what a paste does. Nothing padded a too-narrow one — so importing a 2-column
file into the basic page's 4-column locked grid would have taken the grid down
to 2 columns, while a paste of the same bytes left it at 4.

It now squares every row off to exactly `numCols`. Too wide still alerts,
matching grid.ts. Too narrow pads silently, because a narrow paste says nothing
either and the blanks are what an empty column looks like.

The test for it was run against the pre-fix code and observed to fail with the
grid two columns wide. A regression guard that has never been seen to fail is a
guess about what it guards.

## The move

Under `scientific_cal/`: index.html, home.ts/.js, dev_basic/, src/, topics/.
Left at the root: app.py, tests/, types/, tsconfig.json, robots.txt, sitemap.xml,
and the favicons — a browser asks for /favicon.ico whatever the page path is.

A new umbrella page at `/` lists sections. It carries the Google Search Console
verification meta tag, which has to live at the property root; leaving it only
on the section index would have un-verified the property.

Two things about the backend are worth keeping.

1. **Flask's routes did not change.** They still start with `/api/`. The nginx
   block does the mapping: `proxy_pass http://127.0.0.1:<port>/api/`, with the
   trailing `/api/` doing the substitution. Drop that suffix and every call 404s
   inside Flask. Same trick the /syncthing/ block has always used.
2. **The unprefixed /api/ block is kept.** The backend belongs to the site, not
   to one section, and `/api/health` is how a 404 (no route) is told apart from
   a 502 (route exists, nobody answered).

That second decision has a sting, and it is the CORS-adjacent trap. `page_adv.ts`
called `fetch('/api/…')` with a leading slash. Post-move that resolves to the
unprefixed block — which is kept, so it would have **worked**, and a wrong path
would have passed every test. Every leading-slash path was swept for that
reason, `src/shell/seo.ts`'s spec.json fetch included.

CORS itself needed nothing. Page and API share an origin before and after, and
app.py already records why `flask_cors` is absent. If the API ever gets its own
origin the fix is an exact-origin `add_header` in the nginx block — never a
wildcard, and never in app.py, which has size and row caps but no auth.

### The cards

Five 1200×630 PNGs in `og/` at the repo root, beside the favicons — site
metadata rather than a section's content, and one of the five belongs to the
umbrella page, which is in no section.

Two decisions worth keeping.

**The generator is kept, unlike the favicon's.** `render_favicon.js` was scratch
and thrown away, and the handover carries the recipe as a sentence instead. That
was fine for a file that will never change. These cards carry text from
`spec.json`, so a title change means regenerating — and a script that exists
only as a log entry cannot be re-run. `tools/gen-og.js` plus a `gen-og-images`
flake script.

**`spec.json` needed a new field, and the fallback was refused.** `blog.title`
is 21 characters, `advanced.title` is 62, and `calculator.title` is 120. There
is no rule that turns those three into a card headline. So each level gained a
short `card` string, and a missing one throws rather than falling back to
`title` — a silent fallback would put a 120-character wall on a 1200px image and
nothing would fail.

The test that earns its place asserts the declared URL returns **200** and that
the PNG's own IHDR says 1200×630. A declared `og:image` that 404s looks exactly
like a working one until somebody pastes the link somewhere. Proven by moving a
PNG aside and watching it fail.

### Mobile

One additive `@media (max-width: 900px)` block, the first `@media` rule this
codebase has ever had. Body scrolls, `.app-main` becomes a column, panels take
explicit heights, the ad rail is hidden.

The trap is not obvious and is worth stating plainly: `calc-page.ts` builds both
grids with `viewportHeight: '100%'`, and **100% of an auto height is zero**.
Without an explicit height on the stacked panels the grids render empty while
still existing in the DOM, so only a height assertion catches it.

Four of the fourteen new tests were observed to fail with the media block
removed. The other ten are regression guards that already passed — including the
two desktop cases, which are what prove the block is additive.

### The bug the tests could not see

The phone layout looked right in a screenshot until it did not: the input grid
measured **1428px tall** where 55vh should have capped it near 464.

Every `.panel-grid` section carried `style="flex: 1"` in the HTML. Six of them,
across three files. Two consequences, and the second is the one that mattered:

1. `.panel-grid { flex: 3 }` in `style.css` was **dead code and always had
   been**. The desktop row has always been 1 : 1 : 2, never 3 : 3 : 2.
2. **An inline style cannot be overridden by a media query without
   `!important`.** The mobile block's `flex: none` lost to it, silently.

Fixed by moving the value into CSS as `flex: 1` and deleting all six inline
styles, which leaves the computed desktop result unchanged by construction.
Measured both ways to be sure: desktop 302 : 302 : 604, one row, no scroll,
identical before and after; phone 396 / 396 / 270, stacked.

**It was found by looking at a screenshot, not by a test.** Every mobile test
passed with the broken layout, because they asserted a lower bound on panel
height and a 1428px grid satisfies `> 150` perfectly well. A rendered page is
still worth looking at with your own eyes.

## interp-api as a systemd user service

The user asked for app.py to keep running with VS Code closed. Two things turned
up before writing anything.

**It already survived closing VS Code.** The process had PPID 1 — orphaned and
adopted by init, because the morning's `nohup … &` outlived its shell. So the
stated symptom was already absent. What was actually missing was surviving a
*reboot*, and being managed at all: no restart on crash, no logs anywhere but a
scratchpad file.

**`nix run .` does not run the working tree.** The flake's runApp does
`cd "${self}"`, a store snapshot of git-**tracked** files. nginx serves the repo
directly. So an uncommitted `api_interp.py` edit was live on the page and
invisible to the API at the same time — a quiet contradiction of CLAUDE.md's
"nginx root IS this repo. Build = live." The user chose the working tree for the
service, which closes that gap for the backend.

This reverses the "manual, no systemd unit" decision taken earlier the same day.
Recorded as a reversal rather than quietly overwritten: the earlier decision was
correct given what was known, and the user changed the requirement.

### The trap worth keeping

`ExecStart` points at an out-link, `~/.local/state/nix/interp-api`, not a bare
`/nix/store` path. Checked first, and the check justified the extra step: the
python closure's only GC roots were `/proc/<pid>/maps` entries — **running
processes**. A `nix-collect-garbage` while the service was stopped would have
deleted the interpreter and left a unit that could never start again, with
nothing in the unit file hinting why.

An out-link is a GC root. The cost is one chore: rebuild it after any flake
change, or the service keeps running the old closure. That is now in
`user_todo.md`, replacing the reboot chore it made obsolete.

### Verified, not assumed

1. Parent is PID 54906, `systemd --user`, and the cgroup is
   `…/app.slice/interp-api.service`. No shell is in the chain, so no editor can
   take it down.
2. `kill -9` on the main PID: `NRestarts=1`, new PID, `/api/health` answering
   again within seconds.
3. `/proc/<pid>/cwd` is `/home/opc/nix/webUI` — the working tree, not a store
   snapshot.
4. `Linger=yes` was already set. Worth knowing it was not something this work
   configured; without it a user service dies at logout regardless.

### Reverted to tmux

The user rejected systemd outright. The service was disabled, the unit deleted,
and `systemctl --user daemon-reload` run — no trace left in the user manager.

Replacement is `tools/start-api.sh`: a detached tmux session named `api`, plus a
`@reboot` crontab line. Survives closing VS Code, logging out, and reboot. It
buys something systemd did not — `tmux attach -t api` shows the server's own
output with no log daemon in between — and gives up crash restart, which is now
written down as a known gap rather than an assumption.

Two things carried over from the systemd attempt because they were right
independently of it: the launcher runs the **working tree**, not `${self}`, and
it goes through the **out-link** so the python closure has a real GC root. The
option preview the user picked said `nix run .`; using it would have quietly
reintroduced the committed-only defect they had already chosen against, so the
deviation was flagged rather than taken silently.

One mistake caught before it shipped. The first crontab line logged to
`webUI/.api-boot.log` — inside the nginx root, so it would have been fetchable
at `https://<domain>/.api-boot.log`. Moved to `~/.local/state/api-boot.log`.
**Anything written into this repo is a published file.** That rule has now bitten
in three different shapes today: the fft.zip note, the source maps, and this.

Verified: app.py's parent is `tmux: server`, not a shell; `/proc/<pid>/cwd` is
the working tree; running the script twice leaves exactly one session; and it
starts cleanly under `env -i`, which is what cron will give it.

### The reboot proved it

The user rebooted. Everything came back with nothing typed: nginx, crond, the
`api` tmux session, and /api/health answering.

The detail that makes it proof rather than coincidence is
`~/.local/state/api-boot.log` carrying the script's own output. app.py running
is not evidence cron fired — something else could have started it. The log line
only exists if the crontab entry ran the script.

Also confirmed post-reboot: app.py came up as a boot-PID parented by
`tmux: server` with its cwd on the working tree, all five public URLs 200, the
old URLs still 301, and the suite 129/129.

The three July tmux sessions are gone, as expected. Only `api` has a cron line.

What is still not covered is a crash at 3am. Boot is automatic; supervision is
not, and that is the whole price of dropping systemd. Written down rather than
assumed.
