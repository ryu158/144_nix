# Math & science explainer site

Interactive web explainers for computational concepts: interpolation, smoothing, FFT,
and more topics added over time. Solo-authored.

## Environment

Nix flake dev shell on Oracle Linux 9. Node and Python come from `flake.nix`, not from
the system, but neither is currently exercised by a build step — see Stack.

**Every command runs inside the dev shell.** If a command fails with "not found", the
shell is not active. Do not install the missing tool — `dnf`, `pip install`, and
`npm install -g` are never the right fix here. Enter the shell instead:

```
nix develop            # automatic if direnv is set up
```

`flake.nix` currently provisions Python + Flask/NumPy/SciPy for an `app.py` that does
not exist, and Node + TypeScript that no build script currently uses. Treat these as
available tooling, not evidence that a Flask app or a TS build is in use today.

## Stack

- No framework, no bundler, no build step. Pages are static, hand-written HTML files
  served as-is.
- Vanilla JavaScript, loaded via `<script src="...">` tags: shared components live in
  `dev_basic/` (`grid.js`, `chart.js`, `dual-chart.js`, `ads.js`, `bmc.js`,
  `style.css`), per-topic code lives in `prj/<topic>/`.
- No `package.json` and no npm scripts exist. There is no `npm run dev/build/test`
  today — changes are verified by opening the HTML file directly.

## Layout

```
src/shell/        # Layer 0: base layout, SEO, analytics, nav. Rarely changes.
src/kit/          # Layer 1: shared plot canvas, controls, math utils, tokens.
topics/<slug>/    # Layer 2: one folder per topic. Self-contained.
  spec.json       #   dataset, parameters, formula, metadata
  fixture.json    #   expected numeric outputs from NumPy/SciPy
  blog.md         #   the article
  calculator.ts   #   the interactive demo
  advanced.md     #   optional
tools/fixtures/   # Python scripts that generate fixture.json
```

## Invariants

These are the rules that make the project work. Do not break them without asking.

1. **Never hardcode the topic list.** Navigation, homepage, sitemap, and cross-links are
   generated by iterating over `topics/*/spec.json`. Adding a topic must mean creating
   one folder and nothing else.
2. **Never hardcode colors, fonts, or spacing in a topic.** Import from
   `src/kit/tokens.ts`. If a token is missing, add it to the kit rather than inlining a
   value.
3. **Explanation text ships in static HTML.** JavaScript adds interactivity on top of
   prose already in the document. A page whose content only exists after hydration is a
   bug — search engines may never see it.
4. **Math is verified against fixtures, never by eye.** Every calculator has a test
   asserting it matches `fixture.json` within tolerance. FFT especially can look correct
   and be wrong (bin mapping, 1/N normalization, window scaling).
5. **Extract to the kit on the second use, not the first.** Write it inside the topic
   first. When a second topic needs the same thing, move it to `src/kit/` and generalize
   only as far as the two real cases require. No speculative options.
6. **SEO and analytics live in the shell.** A page author supplies only title,
   description, and social image in `spec.json`. Never add analytics snippets, meta
   tags, or ad code to an individual page.

## Visual grammar

The same meaning always gets the same encoding, on every page. This is what makes
separate topics feel like one site. Defined in `src/kit/tokens.ts`:

| Meaning              | Encoding                 |
| -------------------- | ------------------------ |
| Original data points | Solid dots, `--c-data`   |
| Computed result      | Solid line, `--c-result` |
| Ground truth / ideal | Dashed line, `--c-truth` |
| Discarded / ignored  | Same color, 30% opacity  |
| Active parameter     | `--c-accent` highlight   |

Never assign a color per topic. A fitted curve is `--c-result` in interpolation,
smoothing, and FFT alike.

## Writing style for articles

- Lead with the question a reader would actually search for, not the formal definition.
- One core insight per page. State it early in plain language; derive it afterward.
- The interactive demo deepens the explanation. It never carries it alone.
- The author is a Korean speaker writing in English. Prose in `blog.md` should read as
  natural native English — fix grammar silently while editing, but never change the
  technical meaning. Ask if the intent is ambiguous.

## Working agreements

- Ship one topic completely before starting the next.
- Prefer editing an existing kit component over adding a parallel one.
- When a task touches `src/shell/`, say so explicitly before editing — shell changes
  affect every published page.
- Do not add dependencies without asking. This project stays small on purpose.

## Deferred — do not implement

Monetization (Ko-fi, Carbon Ads, AdSense, Amazon) is postponed until traffic justifies
it. Do not add ad slots, consent banners, or affiliate code. Analytics is the exception
and lives in the shell.
